# 前缀缓存永不命中：请求历史不是严格追加（可直接转给 ZCode 作者）

## 一句话

服务端（本地 OpenAI 兼容引擎）**每轮都在把整个会话重新预填充**，因为客户端的请求体
不是「在末尾追加」——它把每轮那段 `system-reminder`（Plan mode…）**插在新消息之后**，
导致历史中途发生位移，服务端的前缀同一性校验每轮都失败。

## 现象

同一会话连续 6 轮，服务端记录的缓存命中：

```
轮次   消息数   提示词词元   缓存命中   复用路径            首字延迟
1      55       58039        0          root                194.3s
2      57       59674        0          root                206.4s
3      59       60239        0          root                213.1s
4      61       60840        0          root                212.7s
5      63       61156        0          root                214.5s
6      65       61727        0          root                218.3s
```

消息数每轮 +2（正常续写），但命中恒为 0、复用路径恒为 root：
服务端认为这是**全新会话**，于是每轮重算约 6 万词元。

对照组：同一个服务端、同一种规模，只要请求是严格追加的，命中 57756/57784
（99.9%），首字延迟 **1.1 秒**。同一个操作的差距是 **约 200 倍**。

## 直接证据：两个真实请求体的逐字节对比

用一个记录代理（监听客户端连的端口，转发到引擎）抓到连续两次请求，对比：

```
公共前缀：22,002 字符
第一处差异在 22,002：

A: ...</system-reminder>"}]},{"role":"user","content":[{"type":"input_text",
   "text":"<system-reminder>\nPlan mode is active. ...

B: ...</system-reminder>"}]},{"role":"user","content":[{"type":"input_text",
   "text":"Reply with exactly: CAP-A"}]},
   {"role":"assistant","content":[{"type":"output_text","text":"CAP-A"}]},
   {"role":"user","content":[{"type":"input_text",
   "text":"<system-reminder>\nPlan mode is active. ...
```

即：本轮的新消息被**插在那段 system-reminder 之前**，而不是追加到历史末尾。
于是那段提醒在历史中的位置每轮都在移动，从该位置往后的所有字节都与上一轮不同。

## 复现（不依赖你们的客户端）

在一个简单客户端里，把系统提示的第一句换成带秒级时间戳的文本，
服务端立刻出现同样的签名：`命中 0 / 复用路径 root / 同一轮耗时 88 秒`。

## 建议的修法（客户端侧）

让会话历史**严格追加**：

1. 把每轮的 `system-reminder` 放在**固定位置**——例如紧跟在系统提示之后、对话内容之前，
   而不是每轮重新插到新消息后面；
2. 或者不要重复插入内容相同的提醒块（内容一样就不必再发一遍）；
3. 任何每轮都会变的字段（时间戳、会话内计数等）都不要放在前缀里，放在尾部。

## 另外一个服务端问题（顺便一并报）

对于这类请求，服务端自己记录的 `prefill` 用时是 **0.00 秒**，而首字延迟约 200 秒；
时间被记到了 "等待设备" 一栏。这是服务端的计时归属缺陷——
任何依赖该字段做诊断的人都会得出错误结论。如果你们也有类似的对账逻辑，值得核对。

## 对照实验：同一个服务端，另一个客户端是正常的

为了确认不是服务端的问题，我用**同一个引擎实例、同一个端口、同一份配置**，
跑了另一个智能体客户端（走的 Anthropic 消息接口）：

```
轮次  消息数  提示词词元  缓存命中   复用路径              首字延迟
1     86     154449      0          root                  236.4 秒   （冷启动）
2     88     155884      155443     private_endpoint        1.3 秒   （命中 99.7%）
3     90     160886      157010     private_endpoint        6.4 秒   （命中 97.6%）
4     92     164899      161006     private_endpoint        6.7 秒   （命中 97.6%）
```

也就是说：**服务端的复用机制、会话继承和检查点恢复全部正常**，
换一个客户端就能拿到 97% 到 99.7% 的命中，每轮 1.3 到 6.7 秒。
所以问题定位在请求的构造方式上，不在服务端。

这条对照也说明修法是可验证的：改完之后，每轮应该从约 200 秒降到几秒。
