## 一、预填充台阶：找到了，而且翻倍了

### 现象

预填充速度不是平滑衰减，是**一个台阶**：

```
16K   795.8 字/秒      48K   740.6      96K   377.6      173K  351.5      258K  332.4
```

从 96K 到 258K 只掉 7%，但从 48K 到 96K 掉一半。两个独立会话都复现了两侧。

### 定位

逐点细采（每点独立起引擎）：

```
50,182 字   728.7   快
52,120 字   740.6   快
59,872 字   385.2   慢   <-- 台阶在 52120 与 59872 之间
63,748 字   382.6   慢
```

而 `--kvmem-budget 36864` + `--kvmem-gen-reserve 16384` = **53,248**，正落在这个窗口里。

### 判定

把 budget 提到 57344（两者之和变成 73,728）：

```
形状             budget 36864     budget 57344     变化
59,872 字        385.2     ->     735.4            +91%
63,748 字        382.6     ->     726.8            +90%
79,286 字        慢        ->     369.9            仍然慢（符合预测）
```

三个预测全中。另外**把 gen-reserve 抬高、budget 不动，结果几乎一样**（60K→715.9，
96K→353.8），所以阈值是 **B + R 的合计**，不是 B 单独。79,286 那一点同时排除了
sink/recent 计入的可能。

日志独立印证：每个生产实例都报 `device_backend_kv_pages = 832`，832 × 64 = 53,248 = B + R。

### 为什么这条直接打在我们的体验上

```
我们真实负载（实测）：DSH 57,756 字/轮      ZCode 58-62K 字/轮
库存竞技场：                              53,248 字
```

**每一轮都刚好越过台阶，所以一直在慢车道。** 竞技场抬到 73,728 之后，整个真实负载
回到快车道。这不是合成测试的胜利，是真的会到达的请求上 385 对 730 字/秒。

### 代价（实测，不藏）

```
60K 那一档      382.6 -> 734.4 字/秒        +92%
258K 冷读       772 秒 -> 826 秒            -6.6%（预填充 332.4 -> 310.6）
显存            10310 -> 10941 MiB          +631 MiB
召回 3/3        PARROT-5/15/25 逐字全对     通过
```

天花板：budget 73728 能起（竞技场 90,112，显存 11550）；81920 起不来，报得很清楚——
不是显存满，是引擎预留核算差 294 MB。

**已上生产**：`--kvmem-budget 57344`（竞技场 73,728），写在 `start_stack.ps1` 和
`Start-RC3.bat` 里。回滚就是一个参数改回 36864。以后负载若整体上移，旋钮就是
`budget + gen-reserve`，代价是"带来之内 +92%、带来之外 −6.6%"。

### 一个自我纠正，值得记

早先我在 96K 上量过"池子加大没用"，结论是"加大池子反而更慢"。**那次是错的，
因为 96K 在两个预算下都已经在台阶之上，根本看不见台阶。** 只有围绕 50-64K 的细采
才能分辨。正确的说法是：加大竞技场把台阶右移，台阶之下全部提速，台阶之上付约 7%。
两次读数各自在自己的区间里都对。

## 二、SSD 层：会话切换从 71 秒变 4 秒

引擎里有一整套磁盘层，我们的生产配置**从来没开过**（`ssd_enabled: false`）。

### 开关实测（七个组合）

```
--kvmem-disk-path + --kvmem-disk-mib    起得来，ssd_enabled=true
--kvmem-sessions 4                      起得来
--slot-save-path                        拒绝
--auto-save-evicted                     拒绝
--slot-save-path + --auto-save-evicted  拒绝
--disk-kv-path + --disk-kv-restore      拒绝（号称"跨重启存活"的那一套）
```

**"跨重启存活"那一族和 KVMem 配方不兼容**——这是第五次"帮助里有、运行时拒绝"。
所以"重启只需读盘"这个目标在这版二进制上做不到。

### 但 KVMem 自己那层能干另一件事

它让**保留的会话数超过主机内存预算**：空闲会话溢写到 SSD，回来时从盘恢复。

```
（故意把主机预算压到 2 GiB，让溢写便宜地发生）
A 冷算    71.2 秒
B 冷算    75.0 秒     <- B 到来把 A 挤出内存
   写盘 1.60 GB
A 再来     4.3 秒     <- 从 SSD 恢复（预填充字段 0.4，不是 746）
   磁盘命中 815，读盘 1.87 GB

16.6 倍，溢写的代价约 4 秒（5%）。有效恢复速率约 430 MB/s。
```

### 准确的说法

不是"重启变便宜了"，而是：

> 开 `--kvmem-sessions N` 加 SSD 层，保留的长前缀可以超过主机内存的容量；回到被溢写的
> 前缀只需一次读盘，而不是一次冷算。主机预算（12 GiB）只装得下**一个** 258K 会话，
> SSD 层让第二个及以后仍然够得着。

这正对上这台机器的实际用法：两个不同的长前缀（编程 agent 加另一个客户端）现在要抢
同一个热槽位。

代价：这买的是**主机内存容量**，不是上下文长度。上下文天花板仍是制品的 262144。

### 题集结果（温度 0、固定 seed、只差 reasoning_effort）

### 人工复核后，开思考反而输 3 题

MATH 的 23 条 miss 里 15 条是 LaTeX 等价（`58500` vs `58,500`、`\frac` vs `\dfrac`、
`0.09` vs `9/100`、`11(1+\sqrt5)` vs `11\sqrt5+11`…）。复核后 **开 55/60，关 58/60**，
输的三题全是"值算对了、格式写错了"。

### 机制：思考先吃输出预算，答案是剩下的

```
没吐出 \boxed{} 的比例：开 5/60 = 8.3%，关 1/60 = 1.7%
三个独立跑（GSM8K、greedy、MATH）同一个签名：思考块先生成，答案拿剩下的
难题上思考块顶满预算，格式失败率差约 5 倍
```

### 边界（诚实的三个"没测到"）

```
① 172 道题、单步、唯一答案、温度 0 —— 只证明"答对没有"这件事上思考无增量
② 温度 0 测的是能力上限；生产温度 1.0 更抖
③ agentic 干活质量（多步工具、模糊需求、排错）没有覆盖 ——
   而"思考好很多"的体验恰恰在这个维度上
```

### 运营结论（不变）

日常关、钉子开；`medium` 不是可用的中间档（2832-5328 之间乱跳），**预算才是唯一刻度**；
网页类交付要加无头浏览器执行验收（控制台报错数／按钮／动画帧），判分题抓不到死脚本。

## 四、量化格式：两个 4-bit 都没过严格门

PPL 门不可跑（离线评测器不认该制品，服务接口拒 `logprobs`），所以用更严的替代：
同一批提示、温度 0、固定 seed，两引擎逐字对比。

```
格式            8 组逐字一致   分叉性质
int8（对照）     7/8          一个词不同（引擎噪声基线）
rk8v4            5/8          改写级；一组出现事实分叉
rk4v4-e8         3/8          改写级；举例选择都变了
```

精确型任务（代码、长引用逐字、JSON 格式）**三个格式下全一致**；分叉只发生在开放式散文。
但分叉已到"选哪个事实"的层面，对靠工具调用吃饭的 agent 是红线。

**判：生产留 int8。** 4-bit 是有条件备选，触发条件只有显存压力；到那天首选 rk8v4
（8-bit key 还在）。速度快、省显存、洞区召回 3/3 都是真的，但开放式输出会动。

## 五、对外口径：那个"三十万"是除法，不是算力

有客户端界面显示过 309,947 字/秒。查引擎侧同一窗口：

```
客户端显示        309,947 字/秒
引擎真实最快采样   922 字/秒（66 个采样里最高的）
解码均值           53.5 字/秒
引擎侧真实预填充   47,132 字（20 分钟里真正算的）
```

反推：17.3 万 ÷ 30.99 万 ≈ 0.56 秒 —— 那就是九成四命中时的前缀恢复耗时。
**分子按"全算了一遍"计数，分母却是恢复时间。恢复带宽被标成了计算吞吐。**

真实故事反而更好：30 秒 / 12 步能成立，全靠前缀缓存。17.3 万若全冷算要 5-15 分钟。
**关思考省的是"每步新增"，缓存省的是"重复前缀"，两笔账。**

对外一个字都不引用 309,947。

## 六、竞品对照：Strata 攻击的是另一半

`github.com/Niko1221/Strata`（MIT，★23.5k）跑 Qwen3.8-Flash-Next —— 一个 24,576 专家的
MoE，每字只唤醒约 10 个 —— 把热专家留卡上、全部专家放内存、其余给 CPU、SSD 放查表。
官方门槛 12 GB 显存 + 32 GB 内存。

**关键：它和我们打的是不同的瓶颈。**

```
Strata 解决什么            我们解决什么
装不下的是   权重（MoE 专家）      KV 缓存（26 万字上下文）
搬到哪      专家 → 内存/CPU/SSD    KV → 主机内存 + 环形检索
```

B 站那个把三层叠起来用的方案（Strata 管权重 + KVMem 管 KV 位置 + actKV 管 KV 大小），
才能解释为什么它敢报 8 GB——那比 Strata 自己的官方门槛 12 GB 还低。

它的 README 里有两条**独立印证我们的数**：

```
① "第一条消息读全文，约 30,000 字 1 分钟；后面的几秒钟就出来"
   = 500 字/秒冷读 + 秒级复用 —— 和我们 772 秒 → 2.7 秒、332-800 字/秒同形
   → 我们的数在消费级硬件上是正常的，不是慢
② 思考 off/low/medium/high，"Off 最快，High 适合难题"
   = 和我们量过的同一组档位、同一个运营结论
```

它比我们强的地方是**分发与社区**（一键安装、MCP、多卡、社区跑分表、论文、23.5k 星）。
我们强的地方是**单一配置上的深度 + 方法可见**：真冷启动、服务端计时、召回逐字验、
量化格式判定。而它的 README 通篇在讲"怎么测的"——恰好是那个 B 站视频跳过的东西。

## 八、脚本踩坑记录（避免再犯）

```
① 绝不给引擎接"不读的 stderr 管道"。
   它加载时会打日志，管道 64KB 满了就阻塞在绑端口之前 ——
   症状是"进程活着、显存占着、端口不响应"，极像 OOM 或死锁，其实是日志背压。
   这次为此浪费了 40 分钟。一律 DEVNULL 或写文件。

② 绝不给会派生孙进程的东西接管道（旧笔记，再次验证）。

③ 所有请求日志分析必须按 server_instance_id 过滤。
   这个文件是所有曾在 8081 上跑过的引擎共用的（449+ 个实例），
   不限定范围曾经凭空造出"69 个并发请求 / 588 秒排队"的结论。

④ 引擎自报的 timings_seconds.prefill / vision 在真实长任务里读 0.00，
   不可用于归因；只信挂钟时间和缓存行为。
```
