## 一、归因 Stage 0：日志里的解码账，第一次对上了

生产日志（`C:\Bonsai-App\logs\requests-8081.jsonl`，46880 条记录、148 个引擎实例）里筛出
**33 个生产配方实例、940 次请求**逐条拆解：

- `host_exposed + device_wait ≈ 解码墙钟`，中位数比值 **1.036**——这两个字段第一次是自洽的
  （之前 `timings_seconds` 出过 prefill=0.00、vision=0.0、300 秒排队等三起事故）。
- 解码每轮墙钟：短上下文 **38.6 ms** → 130K+ **53.4 ms**（+38%），这 ~15 ms 就是长上下文的每轮税。
- 宿主侧暴露工作只占解码墙 **4–6%**（每轮 1.6 → 3.4 ms）；其余 94–96% 是"等设备"。
- `host_work` 明细里只有三段宿主相位（admission_policy / context_progress /
  stats_publication）——**没有**检索打分、页面搬进搬出、环维护任何一段。

关键结论（也是诚实的部分）：**"等设备"里分不出"GPU 真在算"和"喂不饱"**；而 10-13 观察到的
"长解码烧 5 个核"不在这套表里——那 5 个核的工作发生在不向这些计时器汇报的线程里。
所以 Stage 0 的答案是"执行线程可信、进程级不完整"，下一步 Stage 0b（15 分钟实测：
GPU 占用率 + 逐线程 CPU + 引擎自己的记录，三路同时采）已经写好方案，放进下一个独占窗口。

## 二、P1 窗口化 MTP：谜底揭开了，是 KVMem 明文禁用

- 上游 ninfer 里 `--mtp-attention-window` 是**真机制**：草稿头只看"最前 64 个键 + 最新 N"
  （N ≥ draft+1），做法是把**草稿的页表**重绑到这些页并平移位置，注意力核不变；验证路径完全
  不动，所以贪心输出不变、无损。
- KVMem 拒绝它不是配置错误：公开补丁 `kvmem/kvmem → backends/patches/ninfer-kvmem.patch` 里
  一行守卫 `... && options.speculative.mtp_attention_window == 0`，还有单测专门断言它必须被拒。
  原因合理：草稿页表归 KVMem 管（镜像窗口、窗口滑动时改位置），窗口功能是"第二个主人"，组合
  没实现。**生产这条路在现版本二进制上走不通，换什么参数都没用。**
- 它值多少钱：KVMem 下草稿读的是常驻窗口（B≈57K），不是全部历史，所以论文里 1M 场景的
  +28–44% 搬不过来；先验估计是长上下文解码 **低个位数到 ~10%**。两个不写代码的测法已经排好：
  T1（经典非 KVMem 模式 A/B 开关本身）、T2（生产配方 draft 4 vs 1，量草稿税上限）。跑完
  低于阈值就关线，达标再谈上游。

## 三、容量：账本算清 + 64GB 评估

- 实测每 token 设备 KV **35,905 字节**（两个不同制品独立吻合）；一个 262,144 token 会话在
  宿主内存里约 **8.8 GiB** → 12 GiB 内存池**正好装一个** 258K 会话（与 10-11 的溢写实测一致：
  第二个会话写盘 1.60 GB，回来读 4.3 s vs 冷算 71.2 s）。
- 满载进程：100K 上下文约 **10 GB 物理 / 19 GB 提交峰值**。
- **64 GB 内存买的是容量不是速度**：池子 12→24 GiB（两三个常驻长会话）、消灭页面文件悬崖、
  给后续实验留余量。解码速度、262K 天花板、prefill 速度都不受影响。
- 本机 **2 个内存槽**，现有 2×16G DDR4-2667；升级 = 一对 **2×32G DDR4-3200**（单套、不混插）。
  相比 ActKV（要上游改代码）和 SSD 层（430 MB/s、首触 ~5% 代价），这是桌上最便宜的容量手段。
- ActKV（P6 Phase 1）映射完成：三部分里"打分"一半在我们引擎无信号（LRFU 归因实测是个零）、
  "预算"一半要上游、**只有"压缩"一半真省内存**，约 2.2–2.4 GiB/会话——继续挂着，等 64GB 之后
  或上游先动。

## 四、精度阶梯：跑法就绪，等窗口

- 社区 Swift-1.5 制品：iq2xs（8.77 GiB）已证明能载能跑（60K 处解码 27.8 tok/s、prefill 437.5）；
  **iq3xxs（10.33 GiB）从未载过**。按账算，12G 卡上它只剩 ~0.7 GB 给 KV → 设备窗口只有
  12–16K token（iq2xs 是 61,440）。所以 iq3xxs 在这台机器上的定位是**测质量**（MMLU-Pro 280 题，
  与 76.4 基线同一切片可逐题对比），长上下文速度只能当旁注。
- runbook 已写好：加载器加好 `-Sink/-Recent` 参数、预算降档方案、MMLU 跑法（先备份基线结果
  文件再跑）、清理步骤，全在 `precision-ladder-2026-10-18.md`。
